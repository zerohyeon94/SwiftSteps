# 2026-08-04 - OpenTelemetry와 AI 에이전트 관측의 표준화

> Daily: [[2026-08-04]]
> 분류: IT Trends
> 영역: 클라우드·백엔드·데이터·보안·오픈소스
> 읽기 목표: 5-10분

## 한 줄 요약

OpenTelemetry가 CNCF 졸업 프로젝트가 된 가운데, 생성형 AI·에이전트의 모델 호출·도구 실행·토큰 사용을 공통 관측 데이터로 묶는 시맨틱 컨벤션이 개발 중이어서, 에이전트 품질을 추측이 아닌 trace·metric·log로 진단하는 기반이 커지고 있다.

## 왜 지금 볼 만한가

에이전트 요청은 모델 응답이 느린 것처럼 보여도 실제 원인이 검색, 외부 API, 재시도, 도구 호출 또는 프롬프트 크기일 수 있다. 서비스·모바일 앱·백엔드가 나뉜 환경에서는 각 구간의 이름과 속성이 제각각이면 한 요청을 끝까지 연결해 보기 어렵다. OpenTelemetry(OTel)의 표준화는 특정 관측 벤더의 대시보드보다 먼저, 팀이 어떤 데이터를 같은 뜻으로 기록할지를 정하는 변화다.

## 핵심 내용

### 1. 관측 데이터의 이름을 맞추는 일이 먼저다

OTel의 시맨틱 컨벤션은 trace, metric, log에 붙는 이름·타입·의미의 공통 규칙이다. HTTP 요청, 데이터베이스 호출, 메시지, 클라우드 자원처럼 여러 라이브러리와 도구가 같은 개념을 다룰 때, `서비스 이름`, `작업 이름`, `오류`, `지연 시간`을 같은 계약으로 남기게 한다. 이 계약이 있어야 서로 다른 SDK와 저장소의 데이터를 하나의 요청 흐름으로 상관 분석할 수 있다.

2026년 5월 OTel은 CNCF 졸업(Graduated) 단계에 도달했다. 이는 모든 API가 더는 바뀌지 않는다는 뜻이 아니라, 오픈소스 관측 생태계에서 표준 API·SDK·OTLP 기반 연동이 장기 운영의 기준점이 되고 있다는 신호다. 기존 벤더 전용 계측을 한 번에 제거할 이유는 없지만, 새 계측은 이식 가능한 공통 경계를 우선 검토할 만하다.

### 2. AI 에이전트에서는 하나의 답변이 여러 작업의 합이다

에이전트가 답을 만들 때는 보통 모델 요청, 검색·RAG, 외부 도구 호출, 재시도, 결과 조합이 이어진다. OTel의 GenAI 관련 컨벤션은 이 과정을 `모델`, `작업 유형`, `입·출력 토큰`, `도구 호출`, `대화 식별자` 같은 속성으로 표현하려 한다. 그러면 “45초가 걸렸다”는 현상을 다음처럼 나눠 볼 수 있다.

- 모델 호출 자체의 지연과 토큰 사용량
- 특정 도구나 외부 API의 대기 시간·오류·재시도
- 동일 대화·워크플로 안에서 반복되는 호출 수
- 배포 버전 또는 프롬프트 변경 뒤의 비용·성능 변화

중요한 점은 모든 프롬프트와 도구 결과를 무조건 저장하는 것이 아니다. 공식 문서도 도구 인수·결과처럼 민감할 수 있는 속성에 주의를 둔다. 개인정보, 인증 정보, 의료·결제 데이터가 들어갈 수 있는 서비스는 수집 범위·마스킹·샘플링·보존 기간을 먼저 정해야 한다.

### 3. ‘표준이 개발 중’이라는 상태를 운영에 반영한다

GenAI 시맨틱 컨벤션은 활발히 발전하고 있으며 일부 속성은 이동·폐기 또는 안정성 단계 변경을 거칠 수 있다. 따라서 속성 키를 비즈니스 데이터 모델에 영구 고정하기보다 다음처럼 계층을 나누는 편이 안전하다.

1. 요청 ID, 서비스명, 배포 버전, 오류 분류처럼 팀이 직접 소유하는 최소 공통 필드
2. HTTP·DB·메시징처럼 안정된 OTel 표준 계측
3. GenAI처럼 변경 가능성을 전제로 버전·마이그레이션 전략을 둔 실험 계측

이 구분은 새로운 표준을 쓰지 말자는 뜻이 아니다. 실험 계측을 통해 병목과 비용을 빨리 발견하되, 대시보드·알림·저장 스키마가 한 속성 이름에 과도하게 묶이지 않도록 하자는 뜻이다.

### 4. 개발자가 시작할 때의 작은 단위

처음부터 모든 span과 metric을 설계할 필요는 없다. 한 사용자 요청을 대표하는 trace를 만들고, 모델 호출과 외부 도구 호출에 자식 span을 연결하는 것부터 시작할 수 있다. 각 단계에 서비스·작업명·성공/실패·지연 시간을 일관되게 남기면, 장애 때 “어디에서 느렸는가”를 재현 가능한 질문으로 바꿀 수 있다.

그 다음 토큰 사용량, 캐시 여부, 재시도 횟수처럼 비용·신뢰성에 직접 연결되는 지표를 더한다. 프롬프트 전문이나 도구 결과 전문은 기본 계측 항목으로 넣지 않고, 보안 검토를 거친 제한된 디버그 경로에서만 다루는 것이 좋다.

## 개발자가 알아둘 변화

- 관측성의 핵심 산출물은 대시보드 하나가 아니라, 요청 흐름을 같은 의미로 남기는 데이터 계약이다.
- AI 에이전트의 지연은 모델만의 문제가 아니다. 도구 호출·재시도·검색·네트워크를 분해해 관찰해야 한다.
- GenAI 계측은 비용·성능 진단에 유용하지만, 프롬프트와 도구 데이터의 민감성을 기본 전제로 둬야 한다.
- 표준의 안정성 단계와 버전 변경을 의존성 업그레이드·대시보드 유지보수 계획에 포함해야 한다.

## 용어와 맥락

- **OpenTelemetry (OTel)**: trace, metric, log를 생성·수집·전송하기 위한 오픈소스 관측 표준과 도구 생태계.
- **Trace / Span**: 하나의 요청 전체 흐름과 그 안의 개별 작업 단위를 나타내는 관측 데이터.
- **시맨틱 컨벤션**: 속성 이름·타입·의미를 통일해 여러 도구에서 같은 데이터를 해석하게 하는 규약.
- **OTLP**: OTel 데이터를 수집기나 백엔드로 전송하기 위한 프로토콜.
- **GenAI 계측**: 모델 호출, 토큰 사용, 에이전트·워크플로, 도구 실행을 추적하기 위한 관측 데이터.
