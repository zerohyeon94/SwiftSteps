# 2026-07-15 - Swift 6.2의 Approachable Concurrency

> Daily: [[2026-07-15]]
> 분류: IT Trends
> 읽기 목표: 5-10분

## 한 줄 요약

Swift 6.2는 UI처럼 단일 실행 문맥이 자연스러운 코드에 기본 격리를 줄 수 있게 하고, 실제 병렬 실행은 `@concurrent`처럼 의도를 명시하도록 다듬었다.

## 왜 지금 볼 만한가

Swift·Kotlin 비교 학습을 시작하는 오늘, `var`가 있다고 해서 언제나 동시에 안전하게 바꿀 수 있는 것은 아니라는 다음 단계의 관점을 미리 잡아둘 수 있다. iOS UI 상태를 다룰 때는 상태를 `MainActor`에 묶고, 무거운 작업만 분리한다는 기준이 Kotlin의 Coroutine·Compose 학습에도 이어진다.

## 핵심 내용

- Swift 6.2에는 코드와 모듈을 `MainActor`에 기본 격리하는 선택지가 있다. UI 코드처럼 본래 한 실행 문맥에서 동작해야 하는 경우, 매번 `@MainActor`를 반복하지 않고도 데이터 레이스 위험을 줄이는 방향이다.
- `async` 함수가 호출한 쪽의 실행 문맥을 유지하도록 하는 기능과, 명시적으로 병렬 실행 의도를 나타내는 `@concurrent`가 함께 제시된다. 핵심은 `async`를 만나는 즉시 무조건 백그라운드로 보낸다고 가정하지 않는 것이다.
- 이는 자동 마이그레이션 지시가 아니다. 기존 프로젝트는 모듈 경계, UI 갱신 지점, 실제 무거운 작업을 확인한 뒤 언어 모드와 컴파일러 옵션을 점진적으로 도입해야 한다.

## 내 학습/프로젝트와의 연결

- 오늘 워크북의 `let`·`var`는 **누가 값을 바꿀 수 있는가**를 다룬다. Swift concurrency는 여기에 **어느 실행 문맥에서 바꿀 수 있는가**를 더한다.
- 헬스케어 앱의 걸음 수나 센서 결과를 화면에 반영할 때는 UI 상태 갱신을 한 문맥에 모으고, 분석·변환처럼 비용이 큰 일만 분리하는 설계를 다음 주제로 연결할 수 있다.
- Kotlin에서도 `val`/`var`의 가변성만으로는 동시성 안전이 보장되지 않는다. 이후 Coroutine과 상태 홀더를 배울 때 같은 질문으로 비교한다.
