## 오늘의 학습 목표

- Swift의 `Int`·`Double`·`Bool`·`String`과 타입 추론의 기본 동작을 설명한다.
- 정수 나눗셈 결과가 왜 소수점 없이 잘리는지 예측한다.
- Kotlin에서도 추론된 타입과 명시적 변환이 필요한 경계를 같은 사례로 비교한다.

## 1. 이전 개념 회상 — 5분

### 어제의 실수

- `let`·`val`은 바인딩 재할당을 막지만, 그 자체로 객체 내부까지 항상 불변으로 만들지는 않는다.

### 다시 답하기

- `let session = HealthSession()`에서 `session.steps += 1`이 가능한 이유를 “바인딩”과 “객체 내부 상태”라는 단어를 넣어 한 문장으로 설명한다.

## 2. 새로운 개념 — 10~15분

### Swift 중심 설명

- Swift는 리터럴과 우변 표현식에서 타입을 추론한다. `let stepGoal = 8_000`은 `Int`, `let completion = 0.75`는 기본적으로 `Double`, `let isSynced = true`는 `Bool`로 추론된다.
- 타입 추론은 런타임에 값의 모양을 보고 바꾸는 기능이 아니라 컴파일 단계의 규칙이다. API 경계, 단위, 정밀도를 분명히 해야 할 때는 타입을 명시한다.
- Swift는 `Int`와 `Double`을 자동으로 섞어 계산하지 않는다. 정수 나눗셈은 `Int` 결과를 만들므로, 비율을 얻으려면 나누기 **전에** 적어도 한 쪽을 `Double`로 바꾼다.

```swift
let stepGoal = 8_000              // Int
let completion = 0.75             // Double
let isSynced = true               // Bool
let memberName = "Hyeon"          // String

let completedDays = 7
let totalDays = 10
let truncatedRatio = completedDays / totalDays       // 0, Int 나눗셈
let exactRatio = Double(completedDays) / Double(totalDays) // 0.7

let weeklyGoal: Int = 5           // 단위와 의도를 드러내는 명시적 타입
```

### Kotlin 비교 포인트

- Kotlin도 `val stepGoal = 8_000`을 `Int`, `val completion = 0.75`를 `Double`, `val isSynced = true`를 `Boolean`으로 추론한다.
- Kotlin 역시 숫자 타입을 자동으로 승격해 섞어 계산하지 않는다. 비율을 만들 때는 `toDouble()`을 나누기 전에 적용한다.
- `Float`가 필요하면 두 언어 모두 의도를 명확히 적는 편이 안전하다. Swift는 `0.75 as Float` 또는 문맥 타입, Kotlin은 `0.75f`를 사용한다.

```kotlin
val stepGoal = 8_000              // Int
val completion = 0.75             // Double
val isSynced = true               // Boolean
val memberName = "Hyeon"          // String

val completedDays = 7
val totalDays = 10
val truncatedRatio = completedDays / totalDays       // 0, Int 나눗셈
val exactRatio = completedDays.toDouble() / totalDays // 0.7

val weeklyGoal: Int = 5
```

## 3. 능동 회상 — 10~15분

### 실행 결과 예상

아래 코드는 각각 컴파일될까? `completion`의 추론 타입, 오류 여부, 고치는 방법을 먼저 말하거나 적는다.

```swift
let completed = 7
let total = 10
let completion = completed / total
let isReady = completion >= 0.7
```

내 예상 또는 말로 설명한 핵심:

```kotlin
val completed = 7
val total = 10
val completion = completed / total
val isReady = completion >= 0.7
```

내 예상 또는 말로 설명한 핵심:

### 오류 찾기

화면에 70%를 표시해야 한다. Swift 코드의 오류를 찾고 최소 수정 방향을 적는다. Kotlin에서는 같은 실수를 어떻게 피할지 함께 설명한다.

```swift
let completed = 7
let total = 10
let displayRatio = Double(completed / total)
```

찾은 오류와 수정 방향:

### 빈칸 채우기 또는 코드 순서 맞추기

아래 두 줄 모두 `0.7`을 만들도록 변환 위치를 채운다.

```swift
let ratio = ______(completed) / ______(total)
```

```kotlin
val ratio = completed.________() / total
```

### 정답

- 두 예제 모두 `completion`은 `Int`로 추론되고, `Int >= Double` 비교는 허용되지 않아 컴파일 오류다.
- Swift 수정: `let completion = Double(completed) / Double(total)` 후 `completion >= 0.7`을 비교한다.
- Kotlin 수정: `val completion = completed.toDouble() / total` 후 `completion >= 0.7`을 비교한다.
- 오류 찾기 코드에서 `Double(completed / total)`은 먼저 `Int / Int`를 수행해 `0`을 만든 뒤 `0.0`으로 바꾼다. 변환은 나누기 전에 해야 한다.
- 빈칸: Swift `Double`, `Double`; Kotlin `toDouble`.

### 해설

타입 추론은 보일러플레이트를 줄이지만, 숫자 연산의 의미까지 바꾸지는 않는다. 건강 목표 달성률처럼 비율을 다루는 모바일 화면에서는 “정수 개수”와 “소수 비율”의 타입 경계를 API 모델이나 ViewModel 변환 지점에서 명시해야 0%로 잘리는 오류를 줄일 수 있다.

## 4. Swift → Kotlin 차이 정리 — 5~10분

| 관점 | Swift | Kotlin | 내가 기억할 차이 |
| --- | --- | --- | --- |
| 기본 추론 | 정수 리터럴은 보통 `Int`, 소수 리터럴은 보통 `Double` | 정수 리터럴은 보통 `Int`, 소수 리터럴은 보통 `Double` | 기본 리터럴의 출발점은 매우 비슷하다. |
| 숫자 변환 | `Double(value)`처럼 생성자로 명시 | `value.toDouble()`처럼 변환 함수로 명시 | 두 언어 모두 숫자 자동 승격을 기대하면 안 된다. |
| 실무 사용 | DTO → 화면 모델에서 단위와 정밀도를 타입으로 드러냄 | API 모델 → UI 상태에서도 같은 경계를 명시 | 걸음 수 `Int`와 달성률 `Double`을 섞지 않고 변환 지점을 한 곳에 둔다. |

## 5. 주말 실습 대기 카드

> 오늘 주제 중 직접 실행해야 이해가 분명해지는 내용만 남긴다. 매주 최대 3개만 주말 실습으로 선택한다.

- 실습 후보: 걸음 수와 목표 수로 달성률을 계산하며 `Int` 나눗셈과 `Double` 변환 결과를 Swift·Kotlin에서 비교
- 직접 확인할 질문: `Double(completed / total)`과 `Double(completed) / Double(total)`은 왜 서로 다른가?
- 예상 결과: 전자는 `0.0`, 후자는 `0.7`; Kotlin도 `toDouble()` 적용 시점이 결과를 바꾼다.
- 우선순위: 높음

## 실무 연결

- iOS에서는: HealthKit 또는 BLE에서 받은 정수 측정값을 SwiftUI 진행률에 쓰기 전, `Double` 비율로 바꾸는 위치를 ViewModel에 고정한다.
- Android에서는: Compose UI에 넘기는 `Float`/`Double` 진행률을 API·도메인 모델의 `Int` 값과 구분해 둔다.
- 같은 요구사항에서 선택이 달라지는 이유: 문법은 다르지만 두 언어 모두 숫자 변환을 명시하므로, 화면 상태 모델의 단위 설계가 더 중요하다.
