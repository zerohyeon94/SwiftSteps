## 오늘의 학습 목표

- Swift `let`·`var`와 Kotlin `val`·`var`를 각각 **재할당 가능 여부**로 설명한다.

- Kotlin `val`은 객체 자체를 불변으로 만드는 키워드가 아님을 코드로 확인한다.

## 2. 새로운 개념 — 15분

### Swift 중심 설명

- `let`은 바인딩을 다시 바꾸지 못하게 하고, `var`는 다시 할당할 수 있게 한다.
- 값 타입(`struct`, `enum`, 컬렉션의 값)은 `let`으로 잡으면 그 값의 가변 프로퍼티도 바꿀 수 없다. 값 전체가 상수이기 때문이다.
- 클래스는 참조 자체를 `let`으로 고정한다. 따라서 같은 인스턴스의 `var` 프로퍼티 변경은 가능하지만, 다른 인스턴스로 재할당할 수는 없다.

```swift
struct DailyGoal {
    var count = 0
}

var editableGoal = DailyGoal()
editableGoal.count += 1       // 가능

let fixedGoal = DailyGoal()
// fixedGoal.count += 1       // 오류: let 상수의 프로퍼티를 변경할 수 없음

final class HealthSession {
    var steps = 0
}

let session = HealthSession()
session.steps += 1            // 가능: 참조는 같고, 내부 상태만 변경
// session = HealthSession()  // 오류: 참조를 재할당할 수 없음
```

### Kotlin 비교 포인트

- `val`은 바인딩을 다시 할당하지 못하게 하고, `var`는 재할당을 허용한다.
- Kotlin에서 `val`은 참조를 읽기 전용으로 만들 뿐이다. 객체의 프로퍼티가 `var`이면 그 프로퍼티는 변경할 수 있다.
- 진짜 불변에 가깝게 만들려면 `val` 바인딩뿐 아니라 모델 프로퍼티와 컬렉션의 가변성까지 함께 설계해야 한다.

```kotlin
data class DailyGoal(var count: Int = 0)

var editableGoal = DailyGoal()
editableGoal = editableGoal.copy(count = 1) // 가능

val fixedGoal = DailyGoal()
fixedGoal.count += 1                         // 가능: count가 var
// fixedGoal = DailyGoal()                   // 오류: val은 재할당 불가

class HealthSession(var steps: Int = 0)

val session = HealthSession()
session.steps += 1                           // 가능
// session = HealthSession()                 // 오류
```

## 3. 문제 풀이 — 15분

### 실행 결과 예상

아래 Swift와 Kotlin 코드는 각각 컴파일될까? 컴파일 결과와 이유를 먼저 적는다.

```swift
struct Profile {
    var nickname: String
}

let profile = Profile(nickname: "Zero")
profile.nickname = "Hyeon"
```

내 예상:

```kotlin
data class Profile(var nickname: String)

val profile = Profile(nickname = "Zero")
profile.nickname = "Hyeon"
```

### 정답

- Swift 실행 결과: 컴파일 오류. `profile`은 `let`으로 고정된 값 타입이므로 `nickname` 변경도 값의 변경이다.
- Kotlin 실행 결과: 컴파일된다. `profile` 바인딩은 `val`이지만 `nickname` 프로퍼티가 `var`이므로 내부 상태는 바꿀 수 있다.
- Swift 최소 수정: `var samples = [80, 92]`.
- Kotlin 설명: `samples` 참조는 `val`로 고정되어도, 참조 대상이 `MutableList`라서 요소 추가는 가능하다.
- 빈칸: Swift `var`, Kotlin `var`.

### 해설

`let`과 `val`을 같은 단어로 번역해도 불변성의 범위는 같지 않다. 특히 상태 모델을 설계할 때 Swift에서는 값 타입 + `let`이 강한 변경 방지 장치가 되고, Kotlin에서는 `val`만으로 모델의 내부 변경을 막지 못한다. Kotlin에서는 `val` 프로퍼티와 읽기 전용 컬렉션까지 함께 선택해야 의도를 드러낼 수 있다.

## 4. Swift → Kotlin 차이 정리 — 10분

| 관점 | Swift | Kotlin | 내가 기억할 차이 |
| --- | --- | --- | --- |
| 문법 | `let`은 재할당 불가, `var`는 가능 | `val`은 재할당 불가, `var`는 가능 | 바인딩만 보면 짝이 맞는다. |
| 타입·안전성 | 값 타입을 `let`으로 잡으면 가변 프로퍼티도 변경 불가 | `val` 객체의 `var` 프로퍼티는 변경 가능 | `val`은 깊은 불변이 아니다. |
| 실무 사용 | SwiftUI 입력 상태는 보통 `@State var`, 화면 입력값은 값 타입으로 다룸 | Compose 상태도 `var`와 상태 홀더의 변경 규칙을 분리해 설계 | 상태가 어디서 바뀌는지를 모델과 UI 상태에서 각각 드러낸다. |

- 예상 결과: Swift 값 타입 `let`은 내부 변경 불가, Swift 클래스 `let`과 Kotlin 객체 `val`은 가변 프로퍼티 변경 가능
- 우선순위: 높음

```swift
struct HydrationGoal {
    var cups: Int
}

var goal = HydrationGoal(cups: 6)
goal.cups += 1
```

```kotlin
data class HydrationGoal(var cups: Int)

val goal = HydrationGoal(cups = 6)
goal.cups += 1 // 가능하지만, 재할당은 불가
```

## 실무 연결

- iOS에서는: SwiftUI `View`의 입력값, 네트워크 응답 DTO, 화면 상태를 값 타입과 `let`/`var` 관점으로 구분한다.
- Android에서는: Compose 상태 모델에서 `val` 바인딩만으로는 내부 변경을 막지 못하므로 데이터 클래스 프로퍼티와 컬렉션의 가변성까지 확인한다.
- 같은 요구사항에서 선택이 달라지는 이유: 두 언어 모두 상태 변경 위치를 제한하려 하지만, Swift 값 타입의 기본 성질과 Kotlin 객체/프로퍼티 가변성 모델이 다르다.
