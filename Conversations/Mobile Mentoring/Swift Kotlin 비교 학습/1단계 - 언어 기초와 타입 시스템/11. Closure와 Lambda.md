## 오늘의 학습 목표

- Swift `Closure`와 Kotlin `Lambda`가 나중에 실행할 코드를 값처럼 전달하는 방식을 비교한다.
- 바깥 값을 캡처한다는 말이 실행 시점의 값 복사·참조와 어떻게 연결되는지 구분한다.
- `self` 또는 객체를 오래 붙잡아 순환 참조·불필요한 수명 연장이 생길 수 있는 경계를 읽는다.

## 1. 개념 읽기

![[Assets/2026-09-08 - Closure Lambda - 캡처와 실행 시점.svg]]

그림은 바깥 문맥을 가진 함수 값이 만들어지고 나중에 호출되는 기본 흐름을 보여 준다. 실제 캡처 결과는 값의 종류, 참조, 캡처 목록과 코드의 수명에 따라 달라지므로 그림만으로 메모리 동작을 단정할 수는 없다.

### Swift에서 알아둘 점

Swift의 closure는 이름 없는 함수 값이다. `sorted(by:)`, 비동기 완료 처리, 버튼 동작처럼 “지금 실행하지 않고, 나중에 누군가 호출할 코드”를 전달할 때 쓰인다. closure 본문에서 바깥 범위의 변수·상수·객체를 사용하면 그 문맥을 **캡처**한다.

클래스 인스턴스가 closure를 저장하고 closure가 다시 `self`를 강하게 잡으면, 둘이 서로의 수명을 붙잡는 순환 참조가 생길 수 있다. 그래서 비동기 콜백이나 오래 저장되는 closure에서 `[weak self]` 또는 필요한 값만 `[title]`처럼 명시적으로 캡처하는 이유를 이해해야 한다. 모든 closure에 무조건 `weak`를 붙이라는 규칙은 아니며, 누가 closure를 보관하는지가 먼저다.

### Kotlin에서 알아둘 점

Kotlin의 lambda도 함수처럼 변수에 담거나 인자로 넘길 수 있다. 바깥의 `val`·`var`와 객체 멤버를 사용할 수 있으며, lambda가 실행될 때 그 바깥 문맥을 읽는다. Kotlin/JVM의 세부 구현은 컴파일러와 사용 위치에 따라 달라질 수 있으므로 “항상 객체 하나가 생긴다”처럼 단정하기보다, 코드에서 어떤 객체·변수를 오래 참조하게 되는지 읽는 편이 안전하다.

Kotlin에는 Swift capture list와 완전히 같은 문법이 없지만, lambda 안에서 `this`·외부 객체를 참조하는지, lambda를 누가 얼마나 오래 저장하는지의 질문은 같다. Android에서는 화면·Activity·Fragment보다 더 오래 사는 작업이 화면 객체를 잡지 않도록 lifecycle과 취소 범위를 함께 봐야 한다.

### 두 언어의 핵심 차이

Swift는 `[weak self]`, `[unowned self]`, `[value]` 같은 capture list로 캡처 방식을 호출부에 드러낼 수 있다. Kotlin은 보통 lambda가 참조하는 객체와 coroutine·callback의 수명, 필요하면 지역 변수 분리나 lifecycle-aware API로 경계를 만든다. 두 언어 모두 “closure/lambda가 있어서 위험하다”가 아니라 **보관자와 캡처 대상의 수명 관계**가 핵심이다.

## 2. 개념 선택

> 단일 선택: Closure와 lambda의 설명 중 **옳은 것 하나**를 고르세요.

- [ ] A. closure와 lambda는 선언된 줄에서 반드시 즉시 실행된다.
- [ ] B. 캡처가 있으므로 모든 바깥 값은 항상 깊은 복사된다.
- [ ] C. 나중에 호출할 코드를 값처럼 넘길 수 있으며, 바깥 문맥을 사용할 수 있다.
- [ ] D. Swift의 capture list는 Kotlin lambda를 호출할 수 없게 만든다.

> [!answer]- 정답과 해설
> - 정답: C
> - 해설: closure/lambda는 함수 값으로 전달돼 나중에 호출될 수 있고 바깥 문맥을 참조할 수 있다. 캡처의 구체적 동작은 값·참조와 수명에 따라 읽어야 한다.

## 3. Swift 코드 읽기

> 단일 선택: 다음 코드의 **출력으로 옳은 것 하나**를 고르세요.

```swift
// closure가 바깥에서 읽을 가변 값을 준비한다.
var count = 1
// 지금 출력하지 않고, 나중에 호출할 동작을 report에 저장한다.
let report = { print(count) }
// closure를 호출하기 전에 바깥 값을 변경한다.
count = 2
// 저장해 둔 closure를 이 시점에 실행한다.
report()
```

- [ ] A. `1`
- [ ] B. `2`
- [ ] C. 컴파일 오류
- [ ] D. 아무것도 출력되지 않는다.

> [!answer]- 정답과 해설
> - 정답: B
> - 해설: 이 closure는 바깥의 가변 변수 `count`를 사용하며, 호출 시점의 현재 값 `2`를 읽는다. 특정 값만 고정해 캡처하려면 capture list 같은 별도 표현을 고려한다.

## 4. Kotlin 코드 읽기

> 단일 선택: 다음 코드의 **출력으로 옳은 것 하나**를 고르세요.

```kotlin
// lambda가 바깥에서 읽을 가변 값을 준비한다.
var name = "Swift"
// 지금 출력하지 않고, 나중에 호출할 동작을 report에 저장한다.
val report = { println(name) }
// lambda를 호출하기 전에 바깥 값을 변경한다.
name = "Kotlin"
// 저장해 둔 lambda를 이 시점에 실행한다.
report()
```

- [ ] A. `Swift`
- [ ] B. `Kotlin`
- [ ] C. `name`은 lambda에서 사용할 수 없어 컴파일 오류다.
- [ ] D. lambda는 `println`을 실행할 수 없다.

> [!answer]- 정답과 해설
> - 정답: B
> - 해설: lambda는 바깥의 `name`을 사용할 수 있고 호출 시점에 변경된 값을 읽는다. 이 예시는 캡처의 기본 관찰을 위한 것이며, 장기 보관되는 Android 콜백의 lifecycle 문제와는 별개다.

## 5. 올바른 코드 또는 오류 코드 선택

> 단일 선택: `owner`가 closure를 보관할 수 있고, closure 안에서 `owner`의 메서드를 호출해야 할 때 **순환 참조 위험을 줄이는 Swift 코드 하나**를 고르세요.

### A

```swift
// owner가 나중에 실행할 동작을 action에 등록하려는 코드다.
owner.action = { owner.refresh() }
```

- [ ] A 선택

### B

```swift
// owner가 나중에 실행할 동작을 action에 등록하려는 코드다.
owner.action = { [weak owner] in
    // action 실행 시점에 owner를 사용할 수 있으면 메서드를 호출한다.
    owner?.refresh()
}
```

- [ ] B 선택

### C

```kotlin
// owner가 나중에 실행할 동작을 action에 등록하려는 코드다.
owner.action = { [weak owner] owner.refresh() }
```

- [ ] C 선택

### D

```kotlin
// owner가 나중에 실행할 동작을 action에 등록하려는 코드다.
owner.action = { return weak(owner).refresh() }
```

- [ ] D 선택

> [!answer]- 정답과 해설
> - 정답: B
> - 해설: Swift에서 `[weak owner]`은 closure가 `owner`를 약하게 잡도록 명시하고, 실행 시 optional로 안전하게 처리한다. A가 항상 누수를 뜻하지는 않지만 owner가 closure를 보관하면 순환 참조 위험을 점검해야 한다. C·D는 유효한 Kotlin 문법이 아니다.

## 6. Swift · Kotlin 차이 선택

> 복수 선택: 두 언어의 closure/lambda 수명 경계를 **올바르게 설명한 것을 모두** 고르세요.

- [ ] A. Swift capture list는 `[weak self]`처럼 캡처 방식을 문법으로 드러낼 수 있다.
- [ ] B. Kotlin lambda는 바깥 객체를 참조할 수 없으므로 lifecycle을 고려할 필요가 없다.
- [ ] C. 두 언어 모두 lambda/closure를 누가 보관하는지와 캡처 대상의 수명을 함께 봐야 한다.
- [ ] D. `weak` 캡처는 어떤 코드에서나 무조건 더 올바르다.

> [!answer]- 정답과 해설
> - 정답: A, C
> - 해설: Swift는 capture list를 제공한다. Kotlin도 외부 객체 참조와 비동기 작업의 수명 때문에 lifecycle을 고려해야 한다. 약한 참조는 필요성·실행 보장·소유 관계를 보고 선택한다.
