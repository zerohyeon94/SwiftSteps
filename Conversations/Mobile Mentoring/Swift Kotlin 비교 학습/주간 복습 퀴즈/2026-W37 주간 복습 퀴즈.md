## 문제 1. 값·참조와 변경

> 단일 선택: Swift의 struct와 class, Kotlin의 data class에 관한 설명 중 **옳은 것 하나**를 고르세요.

- [ ] A. Swift struct와 class는 대입할 때 언제나 같은 인스턴스를 공유한다.
- [ ] B. Kotlin data class는 모든 프로퍼티를 자동으로 불변으로 만든다.
- [ ] C. Swift struct는 값 의미를 기본으로 하고, Kotlin data class는 equals·copy 같은 데이터 표현 기능을 제공하지만 내부 var의 변경 가능성은 별도로 봐야 한다.
- [ ] D. 참조 타입을 쓰면 객체 수명과 공유 변경을 고려할 필요가 없다.

> [!answer]- 정답과 해설
> - 정답: C
> - 해설: Swift struct는 대입·전달 때 값 의미가 기본이고, class는 참조 공유가 기본이다. Kotlin data class는 값 중심 기능을 자동 생성하지만 프로퍼티가 var이면 그 내부 상태는 바뀔 수 있다.

## 문제 2. 초기화와 상태 완성

> 단일 선택: 인스턴스를 만들 때 프로퍼티 초기화에 관한 설명 중 **옳은 것 하나**를 고르세요.

- [ ] A. Swift 저장 프로퍼티는 초기값이 없어도 모든 경로에서 자동으로 안전한 값이 들어간다.
- [ ] B. Kotlin의 주 생성자는 필요한 값을 받고 프로퍼티를 함께 선언할 수 있으며, 생성 뒤에 필수 상태가 비어 있지 않게 만드는 역할을 할 수 있다.
- [ ] C. 초기화는 화면이 표시된 뒤에만 처리해야 한다.
- [ ] D. 기본값이 하나라도 있으면 나머지 필수 프로퍼티의 초기화 순서는 중요하지 않다.

> [!answer]- 정답과 해설
> - 정답: B
> - 해설: Kotlin은 주 생성자에서 프로퍼티를 선언·초기화할 수 있다. Swift도 모든 저장 프로퍼티가 사용 전에 초기화되도록 보장한다. 두 언어 모두 ‘반쯤 만들어진 객체’를 정상 상태처럼 쓰지 않도록 설계하는 점이 핵심이다.

## 문제 3. Swift 코드 실행 흐름

> 단일 선택: 다음 Swift 코드의 **실행 결과로 옳은 것 하나**를 고르세요.

~~~swift
struct Badge {
    // 값 타입 Badge의 점수는 인스턴스마다 독립적으로 보관된다.
    var score: Int
}

var first = Badge(score: 10)
var second = first
// second의 변경은 복사된 값에 적용되는지 확인한다.
second.score = 20

print(first.score, second.score)
~~~

- [ ] A. 10 10
- [ ] B. 10 20
- [ ] C. 20 20
- [ ] D. 컴파일 오류

> [!answer]- 정답과 해설
> - 정답: B
> - 해설: Badge는 struct이므로 first를 second에 대입한 뒤 second를 바꾸면 first의 값은 유지된다. 구현의 copy-on-write 최적화와 별개로, 관찰 가능한 의미는 값의 독립성이다.

## 문제 4. Kotlin 제한된 상태 처리

> 단일 선택: 다음 Kotlin 코드의 **실행 결과로 옳은 것 하나**를 고르세요.

~~~kotlin
sealed class LoadState {
    // 화면이 받을 수 있는 상태를 이 파일 안의 하위 타입으로 제한한다.
    data object Loading : LoadState()
    data class Loaded(val count: Int) : LoadState()
}

fun label(state: LoadState): String = when (state) {
    // when은 가능한 상태마다 UI 문구를 정한다.
    LoadState.Loading -> "loading"
    is LoadState.Loaded -> "items=" + state.count
}

println(label(LoadState.Loaded(3)))
~~~

- [ ] A. loading
- [ ] B. items=3
- [ ] C. null
- [ ] D. when에 else가 없어서 항상 컴파일 오류

> [!answer]- 정답과 해설
> - 정답: B
> - 해설: sealed class의 알려진 하위 타입을 모두 처리했으므로 when은 exhaustive하게 판단할 수 있다. Loaded 안에서는 스마트 캐스트가 적용되어 count를 읽는다.

## 문제 5. 타입 검사 뒤 안전한 사용

> 단일 선택: 아래 Swift 코드에서 어떤 선택지가 **타입 검사 뒤 안전하게 이름을 출력하는 코드**인지 고르세요.

### A

~~~swift
// value가 어떤 타입인지 확인하지 않고 바로 멤버에 접근하려는 흐름이다.
let name = value.name
print(name)
~~~

- [ ] A 선택

### B

~~~swift
// as?의 성공한 결과를 지역 상수로 받아 이후에만 프로퍼티를 사용한다.
if let user = value as? User {
    print(user.name)
}
~~~

- [ ] B 선택

### C

~~~kotlin
// 캐스팅 실패 가능성을 무시한 채 결과가 항상 존재한다고 가정한다.
val user = value as User
println(user.name)
~~~

- [ ] C 선택

### D

~~~kotlin
// 타입 검사를 했지만 원래 value를 User처럼 직접 다루려는 흐름이다.
if (value is User) {
    println((value as Any).name)
}
~~~

- [ ] D 선택

> [!answer]- 정답과 해설
> - 정답: B
> - 해설: Swift의 조건부 캐스팅은 실패 가능성을 분기 안에 가둔다. C는 맞지 않는 타입이면 예외가 날 수 있고, D는 Any로 다시 넓혀 name에 접근할 수 없다. Kotlin이라면 value is User 뒤 value.name의 스마트 캐스트를 쓸 수 있다.

## 문제 6. closure·lambda가 나중에 실행될 때

> 단일 선택: 다음 Kotlin 코드의 **실행 결과로 옳은 것 하나**를 고르세요.

~~~kotlin
fun makeReporter(prefix: String): () -> String {
    // 반환할 lambda가 바깥 함수의 prefix를 캡처한다.
    return {
        // 나중에 호출돼도 캡처한 값을 이용해 문자열을 만든다.
        prefix + ": ready"
    }
}

val report = makeReporter("sync")
println(report())
~~~

- [ ] A. sync: ready
- [ ] B. ready만 출력된다.
- [ ] C. prefix는 함수가 끝났으므로 컴파일 오류가 난다.
- [ ] D. lambda는 즉시 실행돼 report에 String만 저장된다.

> [!answer]- 정답과 해설
> - 정답: A
> - 해설: lambda는 바깥 문맥의 prefix를 캡처할 수 있으며, report를 호출하는 시점에 본문이 실행된다. 다만 실제 앱에서는 누가 lambda를 오래 보관하는지와 화면·객체 수명을 함께 확인해야 한다.

## 문제 7. Swift · Kotlin 차이

> 복수 선택: 두 언어의 차이를 **올바르게 설명한 것을 모두** 고르세요.

- [ ] A. Swift의 enum은 연관 값을 가진 case로 상태와 데이터를 함께 표현할 수 있다.
- [ ] B. Kotlin sealed class의 하위 타입은 상태별로 서로 다른 프로퍼티와 동작을 가질 수 있다.
- [ ] C. Swift의 as?와 Kotlin의 as?는 실패할 수 있는 캐스팅을 null 또는 nil 결과로 표현할 수 있다.
- [ ] D. Swift closure와 Kotlin lambda는 바깥 객체를 캡처해도 수명·순환 참조를 검토할 필요가 없다.

> [!answer]- 정답과 해설
> - 정답: A, B, C
> - 해설: enum·sealed class 모두 제한된 상태를 모델링하는 데 쓸 수 있지만 문법과 확장 방식이 다르다. 조건부·안전 캐스팅은 실패를 값으로 다룬다. closure/lambda가 객체를 오래 보관하면 수명과 참조 구조를 반드시 확인해야 한다.
