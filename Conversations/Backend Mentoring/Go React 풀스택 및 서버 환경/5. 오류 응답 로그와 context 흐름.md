## 오늘의 학습 목표

- API 오류를 사용자용 HTTP 응답과 운영자용 원인 로그로 나누는 이유를 이해한다.
- `context.Context`가 요청 취소·마감 신호를 handler에서 service·repository로 전달하는 경로를 읽는다.
- request ID를 연결해 한 요청의 오류를 추적하되 비밀값·원문 오류를 응답에 흘리지 않는 경계를 구분한다.

## 1. 개념과 구조 읽기

![[Assets/2026-09-08 - Go API 오류 경로 - context 로그 응답.svg]]

그림은 `context`와 오류가 계층을 오가는 기본 경로를 요약한다. 실제 오류 코드, 로그 형식, 민감정보 마스킹 규칙은 서비스의 보안·운영 요구에 맞춰 별도로 설계해야 한다.

### 전체 요청 흐름

React가 `POST /focus-sessions`를 호출하면 handler가 요청 본문을 읽고 request ID를 준비한다. service는 제목 규칙 같은 업무 오류를 분류하고 repository는 DB 호출을 수행한다. DB 연결 실패·제약조건 위반처럼 내부 원인이 생기면 상위로 오류를 전달하되, handler는 그것을 그대로 사용자에게 보내지 않는다.

사용자에게는 `400 invalid_input`, `409 conflict`, `500 internal_error`처럼 API 계약에 맞는 안전한 코드·메시지를 준다. 로그에는 request ID, 계층, 오류 종류, 필요한 원인을 남겨 운영자가 같은 요청을 추적할 수 있게 한다. 비밀번호, access token, 주민번호, 전체 SQL·스택 같은 민감한 정보를 응답이나 일반 로그에 섞지 않는 것이 기본이다.

### 오늘 집중할 경계

`context.Context`는 요청의 취소·마감과 요청 범위 값을 전달하는 표준 통로다. 클라이언트가 연결을 끊거나 handler의 timeout이 지나면 `r.Context()`가 취소될 수 있다. 이를 service와 repository까지 넘기면 오래 걸리는 DB 작업도 가능한 범위에서 중단 신호를 받는다.

`context`에 모든 의존성이나 임의의 업무 데이터를 넣는 것은 좋지 않다. DB 핸들, logger, 설정은 명시적 의존성으로 두고, context에는 요청 수명과 request ID처럼 요청 범위의 정보만 제한적으로 둔다. 취소가 왔다고 서버가 절대 즉시 멈춘다는 보장은 없으며, DB 드라이버·외부 API가 context 취소를 지원하는지도 확인해야 한다.

### 환경별 차이

macOS의 로컬 로그 한 줄이 Linux `systemd` journal이나 Windows Event Log에 자동으로 모이는 것은 아니다. 컨테이너에서는 표준 출력의 구조화 로그가 플랫폼 수집기로 전달될 수 있지만, 보존 기간·마스킹·검색 규칙은 운영 환경의 설정이다. 오늘 Day는 실행 검증이 아니라, 코드가 남겨야 할 책임 경계를 읽는 자료다.

## 2. 코드·명령·설정 읽기

> 아래 예시는 읽고 결과·오류·올바른 구성을 판단하기 위한 자료다. Daily 완료를 위해 직접 입력하거나 실행하지 않는다.

```go
// 입력 검증 실패를 다른 내부 오류와 구분하기 위한 업무 오류다.
var ErrInvalidTitle = errors.New("invalid title")

func (s Service) Create(ctx context.Context, title string) (FocusSession, error) {
    // 공백을 제거한 제목이 비어 있는지 service 계층에서 검사한다.
    if strings.TrimSpace(title) == "" {
        return FocusSession{}, ErrInvalidTitle
    }
    // 같은 요청의 취소·마감 신호를 repository까지 전달한다.
    return s.repo.Create(ctx, FocusSession{Title: title})
}

func (h Handler) create(w http.ResponseWriter, r *http.Request) {
    // 응답과 로그에서 같은 요청을 찾을 수 있도록 request ID를 읽는다.
    requestID := requestIDFrom(r.Context())
    // HTTP 요청의 context와 입력값을 service로 넘긴다.
    session, err := h.service.Create(r.Context(), readTitle(r))
    if errors.Is(err, ErrInvalidTitle) {
        // 사용자가 수정할 수 있는 입력 오류는 안전한 400 응답으로 바꾼다.
        writeJSON(w, http.StatusBadRequest, map[string]string{
            "code": "invalid_title", "requestId": requestID,
        })
        return
    }
    if err != nil {
        // 내부 원인은 운영 로그에 남기고 사용자 응답에는 그대로 노출하지 않는다.
        h.logger.Error("create focus session", "request_id", requestID, "error", err)
        writeJSON(w, http.StatusInternalServerError, map[string]string{
            "code": "internal_error", "requestId": requestID,
        })
        return
    }
    // 오류가 없으면 생성된 세션과 201 상태를 반환한다.
    writeJSON(w, http.StatusCreated, session)
}
```

이 코드에서 `ErrInvalidTitle`은 API 계약상 구분 가능한 업무 오류이므로 400으로 바뀐다. 그 밖의 오류는 로그에 원인을 남기되 사용자 응답에는 안전한 코드와 request ID만 보낸다. 실제 서비스에서는 `readTitle`의 decode 오류, DB 제약조건, timeout을 더 세분화할 수 있다.

## 3. 개념 선택

> 단일 선택: 오류 응답과 로그의 역할을 설명한 것 중 **옳은 것 하나**를 고르세요.

- [ ] A. 모든 내부 오류 문자열을 그대로 응답하면 디버깅이 항상 쉬워진다.
- [x] B. request ID는 사용자 응답과 구조화 로그를 연결하는 단서가 될 수 있다.
- [ ] C. 500 응답은 원인과 무관하게 성공을 뜻한다.
- [ ] D. 로그는 저장소 오류를 기록하면 안 된다.

> [!answer]- 정답과 해설
> - 정답: B
> - 해설: request ID는 지원·운영 시 같은 요청을 찾는 데 도움을 준다. 내부 오류를 그대로 노출하면 인프라·SQL·민감정보가 드러날 수 있다.

## 4. 코드·명령 결과 선택

> 단일 선택: 제시된 코드에서 `title`이 공백뿐일 때의 **응답 의미로 옳은 것 하나**를 고르세요.

- [ ] A. repository가 실행되고 201이 응답된다.
- [x] B. `ErrInvalidTitle`이 400과 `invalid_title` 코드로 바뀐다.
- [ ] C. 모든 오류가 500과 DB 로그로만 처리된다.
- [ ] D. context가 있으므로 제목이 자동으로 채워진다.

> [!answer]- 정답과 해설
> - 정답: B
> - 해설: service가 업무 오류를 반환하고 handler가 `errors.Is`로 구분해 400 응답을 만든다. request ID는 오류 원인을 사용자에게 노출하지 않고 추적 단서를 제공한다.

## 5. 오류 원인 또는 올바른 코드·설정 선택

> 복수 선택: 오류·로그·`context`에 대한 **올바른 설명 또는 코드 방향을 모두** 고르세요.

- [x] A. `r.Context()`를 repository로 전달하면 요청 취소·마감 신호를 아래 계층이 받을 수 있다.
- [ ] B. access token은 오류를 재현하기 쉬우므로 응답 JSON에 넣는 편이 좋다.
- [ ] C. `context`를 전역 설정과 DB 연결을 전달하는 만능 컨테이너로 쓰는 것이 권장된다.
- [x] D. DB 드라이버가 context 취소를 지원하는지와 timeout 설정은 별도로 확인해야 한다.

> [!answer]- 정답과 해설
> - 정답: A, D
> - 해설: context 전달은 취소 신호 전달에 유용하지만, 실제 중단 동작은 사용한 API·드라이버에 달려 있다. 의존성은 명시적으로 주입하고 민감정보는 응답에 노출하지 않는다.

## 6. 요청 흐름·환경 차이 선택

> 복수 선택: 요청·데이터 흐름 또는 Linux·Windows·Docker 환경 차이를 **올바르게 설명한 것을 모두** 고르세요.

- [ ] A. React는 500 응답의 SQL 원문을 화면에 반드시 보여 주어야 한다.
- [x] B. handler는 HTTP 코드·응답을 만들고, service·repository의 원인 오류는 로그와 분류를 위해 위로 전달될 수 있다.
- [x] C. 컨테이너 표준 출력 로그가 있다고 해서 보존 기간·마스킹·검색 설정까지 자동으로 완성되는 것은 아니다.
- [ ] D. Windows Event Log와 Linux journal은 같은 경로·도구로 항상 같은 방식으로 읽는다.

> [!answer]- 정답과 해설
> - 정답: B, C
> - 해설: API 응답은 안전한 계약을 유지하고, 내부 원인은 관측 가능한 로그에 남긴다. 로그 수집·보존은 운영 환경에 따라 다르게 구성한다.
