## 오늘의 학습 목표

- HTTP 본문(JSON)과 HTTP 응답(JSON)을 요청·응답 계약으로 읽는다.
- JSON 문법 오류와 “문법은 맞지만 필수값이 없음”을 다르게 다룬다.
- 잘못된 입력은 service·repository로 보내기 전에 4xx 응답으로 끝낼 수 있음을 이해한다.

## 1. 개념과 구조 읽기

`POST /focus-sessions` 같은 API에서 handler는 먼저 본문을 Go 구조체로 읽고(decode), 최소한의 형식·필수값을 검사한 뒤(validate), 그 다음에만 service나 repository에 전달한다. 이 순서는 데이터베이스가 오류 메시지를 대신 만들게 하지 않기 위한 경계다.

- `{ "title": `처럼 끝난 본문은 JSON 문법이 깨졌으므로 decoder가 오류를 낸다.
- `{}`는 문법상 올바르지만 `title`이 비어 있을 수 있다. 이때 애플리케이션 입력 검증이 필요하다.
- 둘 다 클라이언트가 고칠 수 있는 요청 문제이므로 보통 `400 Bad Request`로 설명한다. 실제 API의 오류 형식·상태 코드는 팀 계약에 맞춰 일관되게 정한다.

![[Assets/2026-08-28 - Go JSON 입력 검증 - 요청 흐름.svg]]

> 그림은 JSON decoder 오류와 필수값 검증 실패가 service·repository 전 단계에서 400 응답으로 끝나는 경로를 보여 준다. HTTP 상태 코드와 오류 본문 형식은 API 계약으로 함께 정해야 한다.

## 2. 코드·명령·설정 읽기

> 아래 예시는 읽고 결과·오류·올바른 구성을 판단하기 위한 자료다. Daily 완료를 위해 직접 입력하거나 실행하지 않는다.

```go
type createFocusSessionRequest struct { Title string `json:"title"` }

func createFocusSession(w http.ResponseWriter, r *http.Request) {
    var input createFocusSessionRequest
    if err := json.NewDecoder(r.Body).Decode(&input); err != nil {
        writeJSON(w, http.StatusBadRequest, map[string]string{"error": "invalid JSON"})
        return
    }
    if strings.TrimSpace(input.Title) == "" {
        writeJSON(w, http.StatusBadRequest, map[string]string{"error": "title is required"})
        return
    }
    writeJSON(w, http.StatusCreated, map[string]string{"title": input.Title})
}

func writeJSON(w http.ResponseWriter, status int, body any) {
    w.Header().Set("Content-Type", "application/json; charset=utf-8")
    w.WriteHeader(status)
    _ = json.NewEncoder(w).Encode(body)
}
```

이 예시는 정상 입력을 실제 DB에 저장하지 않는다. 오늘의 범위는 `decoder → 입력 검증 → HTTP 응답`이며, Day 4부터 handler·service·repository의 책임을 나눈다.

## 3. 개념 선택

> 단일 선택: 입력 검증의 역할을 설명한 것 중 **옳은 것 하나**를 고른다.

- [ ] A. JSON decoder는 모든 비즈니스 규칙과 DB 제약조건을 자동으로 검증한다.
- [ ] B. 문법상 올바른 `{}`도 필수 `title`이 비어 있는지 별도로 검사할 수 있다.
- [ ] C. 입력이 잘못되면 항상 PostgreSQL이 먼저 오류를 반환해야 한다.
- [ ] D. `400 Bad Request`는 서버가 요청을 전혀 받지 못했을 때만 쓴다.

> [!answer]- 정답과 해설
> - 정답: B
> - 해설: decoder는 JSON 문법과 구조체 대응을 처리하지만, 필수값·길이·도메인 규칙은 별도의 검증이 필요하다. 이 검증은 repository 이전에도 수행할 수 있다.

## 4. 코드·명령 결과 선택

> 단일 선택: 예시 handler에 본문 `{}`를 보냈을 때의 **결과로 옳은 것 하나**를 고른다.

- [ ] A. decoder가 항상 문법 오류를 내므로 500 응답을 보낸다.
- [ ] B. `Title`이 빈 문자열이므로 `title is required` JSON과 400 응답을 보낸다.
- [ ] C. `Title`이 없으면 Go가 임의의 제목을 생성해 201 응답을 보낸다.
- [ ] D. DB가 없는 예시이므로 HTTP 응답도 보낼 수 없다.

> [!answer]- 정답과 해설
> - 정답: B
> - 해설: `{}`는 유효한 JSON이므로 decode 자체는 성공할 수 있다. Go 문자열의 기본값은 빈 문자열이고, `TrimSpace` 검사에서 400 경로로 간다.

## 5. 오류 원인 또는 올바른 코드·설정 선택

> 복수 선택: JSON 응답을 일관되게 만드는 데 **올바른 설명 또는 코드 순서를 모두** 고른다.

- [ ] A. `Content-Type`은 JSON 본문을 쓴 뒤에 설정해도 항상 같은 효과가 난다.
- [ ] B. 상태 코드와 JSON 오류 본문은 `writeJSON` 같은 공통 함수로 형식을 맞출 수 있다.
- [ ] C. decoder 오류가 나면 `return`해 이후 성공 경로가 이어서 응답을 쓰지 않게 한다.
- [ ] D. 입력 오류를 구분하려면 오류 본문에 개발 서버의 비밀 환경변수를 모두 담아야 한다.

> [!answer]- 정답과 해설
> - 정답: B, C
> - 해설: 응답 헤더와 상태 코드는 본문이 쓰이기 전에 정하는 편이 안전하다. 오류 뒤 `return`하지 않으면 handler가 두 번 응답을 쓰려 할 수 있다. 오류 메시지는 사용자가 고칠 수 있는 범위만 보여 주고 내부 정보는 로그로 분리한다.

## 6. 요청 흐름·환경 차이 선택

> 복수 선택: 요청·데이터 흐름을 **올바르게 설명한 것을 모두** 고른다.

- [ ] A. JSON 문법 오류는 decoder 단계에서 확인하고, service·repository 호출 전에 400으로 끝낼 수 있다.
- [ ] B. 필수값 검증은 JSON 문법 검증과 같은 일이므로 둘을 구분하면 안 된다.
- [ ] C. Day 3의 예시에서 201 응답을 보냈다는 사실만으로 PostgreSQL 저장까지 성공했다고 볼 수는 없다.
- [ ] D. macOS에서 응답 형식을 읽었다면 Linux systemd와 Windows 방화벽 검증도 모두 끝난다.

> [!answer]- 정답과 해설
> - 정답: A, C
> - 해설: 문법 decode와 업무 입력 검증은 서로 다른 단계다. 이 Day는 DB·운영체제 서비스 구성을 다루지 않으므로, 성공 응답이 저장·배포 검증까지 뜻하지 않는다.
