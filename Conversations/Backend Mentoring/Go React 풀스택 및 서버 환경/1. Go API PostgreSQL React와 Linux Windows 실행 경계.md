## 1. 전체 요청 흐름

작은 서비스도 화면, 서버, DB를 한 번에 같은 것으로 보면 오류 위치를 찾기 어렵다. 요청 한 번을 다음 경계로 나누면 각 계층이 무엇을 보장해야 하는지 명확해진다.

```text
사용자
  → React 화면
  → HTTP 요청
  → 리버스 프록시(Nginx 또는 IIS 계열)
  → Go handler
  → service
  → repository
  → PostgreSQL
  → repository
  → service
  → Go JSON 응답
  → React 화면 상태
```

### React의 책임

- 사용자의 입력과 클릭을 받는다.
- API 요청을 보내고 JSON 응답을 해석한다.
- `loading`, `success`, `empty`, `error` 상태를 구분한다.
- DB에 직접 연결하지 않는다.

### Go API의 책임

- HTTP 요청의 경로, 메서드, 헤더, 본문을 해석한다.
- 입력을 검증하고 업무 규칙을 적용한다.
- repository를 통해 DB 작업을 요청한다.
- 성공 데이터 또는 일관된 오류 응답을 JSON으로 반환한다.

### PostgreSQL의 책임

- 테이블, 키, 제약조건으로 데이터 구조와 무결성을 지킨다.
- SQL을 실행하고 트랜잭션 단위로 변경을 확정하거나 되돌린다.
- React 화면이나 HTTP 상태 코드를 직접 결정하지 않는다.

### 서버 환경의 책임

- 프로세스를 실행하고 재시작한다.
- 포트와 방화벽을 관리한다.
- 환경 변수와 비밀값을 안전하게 전달한다.
- 외부 요청을 리버스 프록시에서 Go API 또는 React 정적 파일로 연결한다.
- 로그, 디스크, 메모리, 서비스 상태를 관찰한다.

## 2. 첫 vertical slice

기존 ZipJoong 학습 자산의 `focus_sessions`를 사용한다.

```text
GET /focus-sessions?limit=20
  → Go가 limit를 검증
  → PostgreSQL에서 최근 세션 조회
  → { "items": [...] } JSON 응답
  → React가 목록 또는 empty 상태 표시
```

첫 구현에서는 다음 두 경로만 확인한다.

1. `POST /focus-sessions`로 한 건 생성
2. `GET /focus-sessions`로 목록 조회

인증, 차트, 실시간 갱신, 복잡한 권한은 뒤로 미룬다. 작은 생성·조회 흐름을 두 운영체제에서 똑같이 확인할 수 있어야 환경 차이를 비교하기 쉽다.

## 3. Linux와 Windows에서 달라지는 부분

애플리케이션의 API 계약과 DB 스키마는 가능하면 동일하게 유지한다. 차이는 주로 프로세스 실행, 경로, 권한, 네트워크, 프록시, 로그에서 발생한다.

| 관심사 | Linux 예시 | Windows 예시 |
| --- | --- | --- |
| 셸·자동화 | shell | PowerShell |
| 프로세스 상시 실행 | systemd service | Windows service |
| 리버스 프록시 | Nginx | IIS 또는 별도 리버스 프록시 |
| 방화벽 | 호스트 방화벽 도구와 클라우드 규칙 | Windows Defender Firewall |
| 로그 | journal과 애플리케이션 로그 | Event Viewer와 애플리케이션 로그 |
| 경로 | `/opt/app`, `/etc/app` 같은 경로 | 드라이브와 역슬래시 기반 경로 |
| 권한 | 사용자·그룹·파일 모드 | 사용자·서비스 계정·ACL |

Go는 두 운영체제용 실행 파일을 만들 수 있지만, 실행 파일이 생성됐다는 사실만으로 서버 검증이 끝나지 않는다. 서비스 등록, 재부팅 후 자동 시작, 방화벽, 로그, DB 연결까지 해당 운영체제에서 확인해야 한다.

## 4. Docker와 WSL2가 검증하는 범위

### Docker Linux 컨테이너

Go·PostgreSQL·React 이미지를 같은 네트워크에서 실행하고 환경 변수, 볼륨, 헬스 체크를 검증하기 좋다. 하지만 컨테이너 안에서 성공했다고 해서 실제 Ubuntu 호스트의 SSH, systemd, 호스트 방화벽, 인증서 배치가 검증된 것은 아니다.

### WSL2

Windows PC 안에서 Linux 명령과 Linux용 Go 서버를 시험하기 좋다. 그러나 WSL2 안의 프로세스는 Windows 서비스가 아니며 IIS와 Windows 이벤트 로그를 검증하지 않는다. Windows 네이티브 검증은 Windows용 Go 실행 파일과 Windows 서비스·방화벽·프록시를 별도로 확인해야 한다.

## 5. 학습 순서가 중요한 이유

바로 서버부터 공개하면 오류가 코드, DB, 네트워크, 권한 중 어디에 있는지 분리하기 어렵다. 따라서 다음 순서로 범위를 넓힌다.

1. Go API가 메모리 또는 테스트 데이터로 동작
2. PostgreSQL을 연결하고 데이터 생성·조회 확인
3. React가 같은 API 계약을 소비
4. Linux 한 대에서 프로세스·프록시·방화벽·로그 확인
5. Docker Compose로 구성 재현
6. Windows에서 서비스·프록시·방화벽·로그 확인
7. 두 환경에서 같은 성공·실패 시나리오 비교

## 6. 개념 선택

> 단일 선택: React, Go API, PostgreSQL의 책임을 가장 정확히 설명한 하나를 고른다.

- [ ] A. React가 PostgreSQL에 직접 연결하고 Go는 화면 파일만 전달한다.
- [ ] B. React는 UI와 API 호출을, Go는 요청·업무 규칙을, PostgreSQL은 데이터 저장과 무결성을 담당한다.
- [ ] C. PostgreSQL이 HTTP 상태 코드와 React 화면 상태를 결정한다.
- [ ] D. Go API가 있으면 리버스 프록시와 서비스 관리가 필요 없다.

> [!answer]- 정답과 해설
> - 정답: B
> - 해설: 화면, API, 데이터 저장의 책임을 분리해야 계약과 오류 위치를 확인할 수 있다. React가 DB에 직접 연결하면 DB 자격 증명과 내부 구조가 클라이언트에 노출된다.

## 7. 요청 흐름 선택

> 단일 선택: 목록 조회 요청의 올바른 순서를 고른다.

- [ ] A. React → PostgreSQL → Nginx → Go handler → React
- [ ] B. React → 리버스 프록시 → Go handler → service → repository → PostgreSQL → JSON 응답 → React
- [ ] C. PostgreSQL → React → Go service → systemd → React
- [ ] D. React → systemd → PostgreSQL → repository → Go handler

> [!answer]- 정답과 해설
> - 정답: B
> - 해설: 외부 HTTP 요청은 프록시와 Go의 HTTP 경계를 지나 업무·데이터 계층으로 이동한 뒤 JSON 응답으로 돌아온다. systemd는 요청마다 호출되는 계층이 아니라 Go 프로세스를 관리한다.

## 8. Linux 환경 선택

> 복수 선택 가능: 실제 Ubuntu 서버에서 별도로 확인해야 하는 항목을 모두 고른다.

- [ ] A. systemd 서비스의 시작·중지·재시작
- [ ] B. 호스트 방화벽과 외부 공개 포트
- [ ] C. SSH 사용자와 파일 권한
- [ ] D. Swift Optional 언래핑 규칙

> [!answer]- 정답과 해설
> - 정답: A, B, C
> - 해설: Linux 서버 운영에서는 프로세스 관리, 네트워크 공개 범위, 사용자·권한을 실제 호스트에서 확인해야 한다. Swift 언어 규칙은 서버 환경 검증 대상이 아니다.

## 9. Windows 환경 선택

> 복수 선택 가능: WSL2만으로 완료했다고 볼 수 없는 Windows 네이티브 검증을 모두 고른다.

- [ ] A. Go 실행 파일의 Windows 서비스 등록
- [ ] B. Windows Defender Firewall 규칙
- [ ] C. IIS 또는 Windows용 리버스 프록시 연결
- [ ] D. WSL2 안에서 Linux 셸 명령 실행

> [!answer]- 정답과 해설
> - 정답: A, B, C
> - 해설: WSL2는 Linux 개발 환경이다. Windows 서비스, Windows 방화벽, IIS는 Windows 네이티브 환경에서 따로 검증해야 한다.

## 10. 첫 구현 범위 선택

> 단일 선택: 환경 차이를 학습하기 위한 첫 vertical slice로 가장 적절한 하나를 고른다.

- [ ] A. 인증, 실시간 통신, 차트, 관리자 권한을 모두 포함한 전체 서비스
- [ ] B. 화면 없이 DB만 설치하고 외부 연결을 모두 허용한 서버
- [ ] C. `focus_sessions` 생성·조회 API와 React 목록의 성공·빈 결과·오류 상태
- [ ] D. 운영체제별 UI 색상만 비교하는 정적 페이지

> [!answer]- 정답과 해설
> - 정답: C
> - 해설: 작은 생성·조회 흐름은 React, Go, PostgreSQL, 서버 환경을 모두 지나면서도 실패 지점을 분리할 수 있다. 기능을 한꺼번에 늘리면 환경 학습보다 기능 복잡도가 커진다.
