> 로컬의 별도 연습 폴더에서 최소 Go 서버를 실행하고, 성공 응답과 존재하지 않는 경로의 실패 응답을 각각 실제 명령과 출력으로 확인한다. 비밀번호·토큰·실제 운영 접속 문자열은 사용하거나 기록하지 않는다.

## 오늘의 학습 목표

- `http.ServeMux`가 메서드와 경로를 handler에 연결하는 위치를 설명한다.
- `GET /health` 성공 경로와 정의하지 않은 경로의 `404 Not Found` 실패 경로를 로컬에서 구분한다.
- 오늘의 서버가 React·PostgreSQL을 아직 연결하지 않은 최소 경계임을 확인한다.

## 1. 개념과 구조 읽기

### 최소 요청 흐름

```text
curl 또는 나중의 React
  → http://localhost:8080/health
  → Go http.Server
  → ServeMux의 "GET /health" handler
  → HTTP 200 + JSON 응답
```

![[Assets/2026-08-24 - Go HTTP 라우팅 결과 구분.svg]]

> `200`, `404`, 연결 실패는 요청이 도달한 단계가 다르다. 이 그림에서는 서버 프로세스·포트, ServeMux의 경로 매칭, handler 응답을 분리해 본다.

Day 1에서 본 전체 서비스 흐름 중 오늘은 `Go HTTP 서버 → handler → HTTP 응답`만 떼어 검증한다. React는 아직 요청을 보내지 않고, PostgreSQL도 아직 연결하지 않는다. 이 범위를 작게 두면 포트가 열리지 않는 문제, 라우팅이 맞지 않는 문제, JSON 응답이 잘못된 문제를 데이터베이스나 프런트엔드 문제와 섞지 않을 수 있다.

Go 1.22 이상의 `http.ServeMux`는 `"GET /health"`처럼 메서드와 경로를 함께 패턴으로 쓸 수 있다. 이 파일의 코드는 그 문법을 사용한다. `go version`이 1.22보다 낮다면 메서드별 분기를 직접 두거나 Go 버전을 먼저 확인해야 하며, 낮은 버전에서 같은 패턴을 그대로 실행한 결과를 라우팅 실패로 오해하면 안 된다.

### 성공과 실패를 함께 보는 이유

`GET /health`가 `200 OK`를 반환하는 것만으로 라우팅을 모두 이해했다고 볼 수는 없다. 정의하지 않은 `GET /missing`도 호출해 기본 `404 Not Found`가 오는지 확인하면, 서버가 실행 중이지만 해당 경로에는 handler가 없다는 사실을 구분할 수 있다. 연결 거부(`connection refused`)는 서버가 포트에서 듣고 있지 않은 문제라서 404와 전혀 다른 층의 실패다.

## 2. 코드·명령·설정 읽기

별도 연습 폴더에서 다음 파일 하나를 만든다. 기존 프로젝트의 `main.go`를 덮어쓰지 않는다.

```go
package main

import (
    "encoding/json"
    "log"
    "net/http"
)

func main() {
    mux := http.NewServeMux()

    mux.HandleFunc("GET /health", func(w http.ResponseWriter, r *http.Request) {
        w.Header().Set("Content-Type", "application/json; charset=utf-8")
        json.NewEncoder(w).Encode(map[string]string{"status": "ok"})
    })

    server := &http.Server{Addr: ":8080", Handler: mux}
    log.Println("listening on http://localhost:8080")
    log.Fatal(server.ListenAndServe())
}
```

연습 폴더에서의 실행 순서는 다음과 같다.

```text
go mod init example.com/focus-api
go run .
```

두 번째 터미널에서 다음 요청을 보낸다.

```text
curl -i http://localhost:8080/health
curl -i http://localhost:8080/missing
```

## 3. 구현·환경 테스트

### 실행 대상

- Go 1.22 이상이 설치된 로컬 연습 폴더
- `main.go`의 `GET /health` handler
- 별도 터미널의 `curl` 요청 두 개

### 확인할 성공 결과

- [ ] `go run .`가 `listening on http://localhost:8080` 로그를 남기고 종료하지 않는다.
- [ ] `curl -i http://localhost:8080/health`가 `HTTP/1.1 200 OK`와 `{"status":"ok"}`에 해당하는 JSON 본문을 반환한다.

### 확인할 실패 결과

- [ ] `curl -i http://localhost:8080/missing`가 `404 Not Found`를 반환한다.
- [ ] 서버를 종료한 뒤 같은 `/health` 요청이 404가 아니라 연결 실패가 됨을 확인하거나, 그 차이를 명령 출력으로 구분한다.

> [!tip] 오류를 구분하는 기준
> `404`는 서버까지는 도달했지만 해당 경로에 맞는 handler가 없다는 뜻이다. 연결 실패는 프로세스가 실행 중인지, 포트가 다른 프로세스에 이미 사용 중인지, 주소가 맞는지를 먼저 확인해야 한다. 두 결과를 같은 “API 오류”로 묶지 않는다.

## 4. 개념 선택

> 단일 선택: `http.ServeMux`의 역할을 가장 정확히 설명한 하나를 고른다.

- [ ] A. PostgreSQL 테이블의 제약조건을 관리한다.
- [ ] B. 들어온 HTTP 요청의 메서드·경로를 맞는 handler로 연결한다.
- [ ] C. React 컴포넌트를 브라우저에 렌더링한다.
- [ ] D. 운영체제 부팅 시 Go 바이너리를 자동 실행한다.

> [!answer]- 정답과 해설
> - 정답: B
> - 해설: ServeMux는 HTTP 요청을 패턴에 따라 handler로 보낸다. DB 무결성, 화면 렌더링, 프로세스 자동 시작은 각각 다른 계층의 책임이다.

## 5. 요청 흐름 선택

> 단일 선택: `GET /health` 요청의 올바른 흐름을 고른다.

- [ ] A. curl → PostgreSQL → React → handler → JSON
- [ ] B. curl → Go 서버 → ServeMux → `GET /health` handler → HTTP 200 JSON
- [ ] C. curl → systemd → repository → PostgreSQL → HTTP 200
- [ ] D. curl → Go 서버 → 정의되지 않은 `/missing` handler → HTTP 200

> [!answer]- 정답과 해설
> - 정답: B
> - 해설: 오늘의 범위에는 React·repository·PostgreSQL이 없다. Go 서버가 요청을 받고 ServeMux가 handler로 연결한 뒤 응답을 쓴다.

## 6. 오류 원인 또는 올바른 설정 선택

> 복수 선택 가능: `curl http://localhost:8080/health`가 연결 실패일 때 먼저 확인할 항목을 모두 고른다.

- [ ] A. `go run .` 프로세스가 실행 중인지
- [ ] B. 서버 주소가 `:8080`인지와 요청 포트가 같은지
- [ ] C. 다른 프로세스가 8080 포트를 이미 점유했는지
- [ ] D. `/missing` 경로가 404를 반환하는지

> [!answer]- 정답과 해설
> - 정답: A, B, C
> - 해설: 연결 실패는 서버 도달 전 단계의 문제다. `/missing`의 404는 서버에 연결된 뒤 라우팅에서 발생하므로, 연결 실패의 첫 점검 대상이 아니다.

## 7. 환경 차이 선택

> 복수 선택 가능: 오늘의 macOS 로컬 테스트가 아직 대신하지 못하는 검증을 모두 고른다.

- [ ] A. Ubuntu의 systemd 서비스 등록과 재부팅 후 시작
- [ ] B. Windows 서비스·Windows Defender Firewall 검증
- [ ] C. Docker Compose의 API·DB 네트워크 검증
- [ ] D. `GET /health`의 로컬 HTTP 응답 확인

> [!answer]- 정답과 해설
> - 정답: A, B, C
> - 해설: 로컬 실행은 handler와 HTTP 기본 동작을 검증한다. 운영체제 서비스 관리와 방화벽, 컨테이너 네트워크는 각각 나중의 환경 Day에서 별도로 확인해야 한다.
