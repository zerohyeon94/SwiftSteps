## 1. 개념과 구조 읽기

`POST /focus-sessions`를 예로 들면 handler는 HTTP 본문을 읽고 응답 상태를 정한다. service는 ‘제목이 비어 있으면 안 된다’, ‘같은 요청을 어떻게 처리할지’처럼 유스케이스의 규칙을 결정한다. repository는 SQL·드라이버·테이블 세부사항을 사용해 데이터를 저장하거나 조회한다.

![[Assets/2026-09-02 - Go API 계층 - handler service repository 책임.svg]]

그림은 요청이 각 계층을 지나는 기본 흐름과 책임을 보여 준다. 모든 프로젝트에 반드시 세 계층이 필요하다는 뜻은 아니며, 규모와 변경 가능성에 맞게 경계를 정한다.

### handler: HTTP 경계

handler는 `http.Request`와 `http.ResponseWriter`를 아는 곳이다. JSON decode 오류, HTTP 상태 코드, 응답 헤더처럼 전송 형식의 문제를 다룬다. service가 HTTP 상태 코드나 `ResponseWriter`를 직접 알게 하면 업무 규칙이 웹 전송 방식에 묶이기 쉬워진다.

### service: 유스케이스 경계

service는 여러 repository 호출을 조합하고 업무 규칙을 적용한다. 예를 들어 제목을 정리하고, 중복 생성 정책을 판단하고, 저장할 `FocusSession`을 만든다. service의 입력·출력은 가능한 한 HTTP나 SQL 타입보다 도메인 타입과 오류로 표현한다.

### repository: 저장소 경계

repository는 `database/sql`, SQL 문, 행 스캔 같은 데이터 접근 세부사항을 가진다. `INSERT`가 실패했을 때의 드라이버 오류를 상위에 전달하되, handler가 SQL 문자열을 알아야 하게 만들지는 않는다. 저장소를 메모리 구현으로 바꾸거나 테스트 대역으로 바꿀 여지도 이 경계에서 생긴다.

### 인터페이스를 어디에 둘까

Go에서는 모든 계층에 큰 인터페이스를 미리 만들 필요가 없다. service가 repository의 작은 기능 하나만 필요하다면 **service가 필요한 메서드만 정의한 작은 인터페이스**를 두는 편이 읽기 쉽다. 인터페이스는 구현 목록이 아니라 의존하는 쪽의 요구를 표현한다.

## 2. 코드·명령·설정 읽기

> 아래 예시는 읽고 결과·오류·올바른 구성을 판단하기 위한 자료다. Daily 완료를 위해 직접 입력하거나 실행하지 않는다.

```go
type FocusSession struct {
    ID    int64
    Title string
}

type FocusSessionRepository interface {
    Create(ctx context.Context, session FocusSession) (FocusSession, error)
}

type FocusSessionService struct {
    repo FocusSessionRepository
}

func (s FocusSessionService) Create(ctx context.Context, title string) (FocusSession, error) {
    title = strings.TrimSpace(title)
    if title == "" {
        return FocusSession{}, errors.New("title is required")
    }
    return s.repo.Create(ctx, FocusSession{Title: title})
}

func (h Handler) create(w http.ResponseWriter, r *http.Request) {
    var input struct{ Title string `json:"title"` }
    if err := json.NewDecoder(r.Body).Decode(&input); err != nil {
        writeJSON(w, http.StatusBadRequest, map[string]string{"error": "invalid JSON"})
        return
    }
    session, err := h.service.Create(r.Context(), input.Title)
    if err != nil {
        writeJSON(w, http.StatusBadRequest, map[string]string{"error": err.Error()})
        return
    }
    writeJSON(w, http.StatusCreated, session)
}
```

이 예시에서 handler는 JSON 오류를 400으로 바꾸고 service를 호출한다. service는 제목 정리·필수값 규칙을 적용한 뒤 repository에 전달한다. 실제 서비스에서는 `title is required`처럼 사용자에게 보여 줄 오류와 내부 저장소 오류를 같은 방식으로 노출하지 않도록 오류 분류를 더 설계할 수 있다.

## 3. 개념 선택

> 단일 선택: 계층의 책임을 설명한 것 중 **옳은 것 하나**를 고르세요.

- [ ] A. handler는 SQL 문자열과 행 스캔을 직접 맡아야 계층이 줄어든다.
- [ ] B. service는 HTTP 상태 코드와 응답 헤더를 가장 먼저 정하는 계층이다.
- [ ] C. repository는 저장소 접근 세부사항을 감추고, service는 유스케이스 규칙을 조합할 수 있다.
- [ ] D. 모든 Go 프로그램은 파일 하나마다 반드시 세 개의 인터페이스가 필요하다.

> [!answer]- 정답과 해설
> - 정답: C
> - 해설: repository는 DB·외부 저장소의 접근 세부사항, service는 유스케이스 규칙을 주로 맡는다. 작은 프로그램에서 경계를 생략할 수는 있지만, 큰 인터페이스를 무조건 미리 만드는 규칙은 없다.

## 4. 코드·명령 결과 선택

> 단일 선택: 위 예시에서 JSON 본문이 `{ "title": "   " }`일 때의 **결과로 옳은 것 하나**를 고르세요.

- [ ] A. JSON 문법이 맞으므로 repository가 빈 제목을 그대로 저장한다.
- [ ] B. service가 공백을 제거한 뒤 `title is required` 오류를 반환하고 handler는 400 JSON 응답을 만든다.
- [ ] C. handler가 201을 먼저 쓴 뒤 service 오류를 무시한다.
- [ ] D. HTTP 요청이므로 Go 컴파일러가 자동으로 제목을 채운다.

> [!answer]- 정답과 해설
> - 정답: B
> - 해설: JSON decode는 성공하지만 service의 `TrimSpace` 뒤 제목이 비어 있으므로 오류가 반환된다. handler가 이를 400 응답으로 변환한다.

## 5. 오류 원인 또는 올바른 코드·설정 선택

> 복수 선택: 책임 분리에 대한 **올바른 설명 또는 코드 방향을 모두** 고르세요.

- [ ] A. `r.Context()`를 service와 repository까지 전달하면 요청 취소·마감 신호를 함께 전달할 수 있다.
- [ ] B. handler가 repository의 SQL 오류 메시지를 아무 가공 없이 사용자에게 항상 노출해야 한다.
- [ ] C. service가 필요로 하는 `Create` 메서드만 작은 repository 인터페이스로 표현할 수 있다.
- [ ] D. repository를 만든 뒤에는 테스트에서 메모리 구현이나 대역을 만들 수 없다.

> [!answer]- 정답과 해설
> - 정답: A, C
> - 해설: context는 요청 수명과 취소를 아래 계층에 전달하는 데 쓸 수 있다. 내부 DB 오류에는 민감한 세부사항이 있을 수 있으므로 사용자용 오류와 로그를 분리한다. 작은 인터페이스는 테스트 대역을 만드는 데도 도움이 된다.

## 6. 요청 흐름·환경 차이 선택

> 복수 선택: 요청·데이터 흐름 또는 환경 경계를 **올바르게 설명한 것을 모두** 고르세요.

- [ ] A. React는 HTTP JSON 계약을 사용하므로 Go service의 내부 구조체와 SQL 테이블을 직접 알아야 한다.
- [ ] B. `handler → service → repository`는 한 방향의 의존성을 만들기 위한 예시이며, repository가 HTTP 응답을 만들 필요는 없다.
- [ ] C. macOS에서 메모리 repository로 읽어 본 성공 흐름은 PostgreSQL 제약조건과 Linux·Windows 운영 검증까지 완료했다는 뜻이다.
- [ ] D. handler가 JSON 응답을 만들고 repository가 영속 저장을 맡으면, DB 드라이버 교체의 영향 범위를 repository 근처로 제한하기 쉬워진다.

> [!answer]- 정답과 해설
> - 정답: B, D
> - 해설: 프론트엔드는 API 계약을 보고, 내부 계층과 SQL은 서버 내부의 관심사다. 메모리 구현에서의 성공은 실제 DB·운영 환경 검증을 대신하지 못한다.
