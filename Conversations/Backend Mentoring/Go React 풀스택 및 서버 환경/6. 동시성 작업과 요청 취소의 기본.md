## 오늘의 학습 목표

- 한 HTTP 요청 안에서 서로 독립적인 조회를 병렬로 시작할 때, 결과 수집과 오류 처리를 분리해 읽는다.
- client disconnect와 timeout의 취소 신호가 handler에서 service·repository·외부 API까지 내려가는 이유를 이해한다.
- goroutine·channel이 있다고 해서 자동으로 빠르고 안전해지는 것은 아니며, 종료·버퍼·공유 상태의 책임을 설계해야 함을 구분한다.

## 1. 개념과 구조 읽기

![[Assets/2026-09-09 - Go API 동시성 - 취소와 결과 수집 흐름.svg]]

그림은 하나의 요청 context가 병렬 작업 두 개에 전달되고, 결과 또는 취소 신호로 돌아오는 기본 흐름을 보여 준다. 실제 서비스의 DB 연결 수, 외부 API 제한, 재시도 정책과 작업 우선순위는 별도로 설계해야 한다.

### 전체 요청 흐름

예를 들어 React 대시보드가 최근 집중 세션과 오늘의 요약을 함께 요청한다고 하자. 두 데이터가 서로 의존하지 않는다면 service는 DB 조회와 요약 API 호출을 동시에 시작할 수 있다. 각각의 작업은 결과 또는 오류를 channel로 보내고, service는 둘을 모아 하나의 응답 DTO를 만든다.

이때 병렬 처리의 목적은 goroutine 수를 늘리는 것이 아니라, **서로 기다릴 필요가 없는 I/O 대기 시간을 겹치는 것**이다. 두 작업이 같은 DB 연결·같은 전역 map·같은 외부 API 한도를 경쟁하면 오히려 대기와 실패가 커질 수 있다. 작업을 나누기 전에 입력·출력·공유 자원·실패 시 응답 규칙을 먼저 정한다.

### 취소는 요청의 수명을 아래로 전달한다

HTTP 요청의 context는 클라이언트가 연결을 끊거나 서버가 정한 마감 시간이 지나면 Done channel을 통해 취소를 알릴 수 있다. handler가 받은 context를 service와 repository에 전달하면, DB 드라이버나 HTTP client가 지원하는 범위에서 오래 걸리는 I/O를 중단할 기회를 얻는다.

그러나 context 취소는 goroutine을 강제로 죽이는 명령이 아니다. 각 작업이 ctx.Done을 select로 확인하거나 context를 받는 QueryContext·http.NewRequestWithContext 같은 API를 사용해야 한다. 채널 송신만 하던 goroutine은 호출자가 이미 응답을 끝낸 뒤에도 막힐 수 있으므로, 송신 시에도 취소 경로를 함께 둔다.

### 종료·버퍼·공유 상태의 경계

channel을 버퍼 없이 쓰면 수신자가 받을 때까지 송신자가 기다린다. 이는 필요한 동기화일 수 있지만, 요청이 먼저 취소된 경우 송신 goroutine이 영원히 기다리는 원인이 될 수 있다. 결과 개수를 알고 있고 작은 결과만 보낼 때는 충분한 버퍼를 두거나, 송신 쪽 select에서 ctx.Done을 처리하는 방식을 검토한다.

또한 여러 goroutine이 같은 slice·map·카운터를 동시에 바꾸면 data race가 생길 수 있다. 이번 Day의 예시는 channel로 결과를 한 곳에 모아 공유 변경을 최소화한다. 복잡한 공유 상태가 필요하면 mutex·single owner goroutine·불변 결과 중 어떤 모델이 책임을 가장 명확히 하는지 선택한다.

### 환경별 차이

macOS 로컬에서 짧은 요청이 통과했다고 Linux 서버의 timeout, Kubernetes 종료 신호, Windows 서비스 재시작 상황까지 검증된 것은 아니다. Linux의 reverse proxy·systemd, Windows의 서비스 관리자, 컨테이너 오케스트레이터는 각자 요청 종료와 프로세스 종료 시간을 다르게 전달할 수 있다. 코드의 context 흐름과 실제 운영 환경의 종료 정책을 같은 것으로 섞지 않는다.

## 2. 코드·명령·설정 읽기

아래 예시는 읽고 결과·오류·올바른 구성을 판단하기 위한 자료다. Daily 완료를 위해 직접 실행하지 않는다.

~~~go
type Dashboard struct {
    Sessions []FocusSession
    Summary  Summary
}

type result[T any] struct {
    // 어떤 작업의 결과인지와 오류를 한 channel 메시지로 전달한다.
    value T
    err   error
}

func (s Service) Dashboard(ctx context.Context) (Dashboard, error) {
    // 두 작업의 결과가 각각 한 번씩 들어올 수 있도록 버퍼를 둔다.
    sessionsCh := make(chan result[[]FocusSession], 1)
    summaryCh := make(chan result[Summary], 1)

    go func() {
        // repository에는 같은 요청의 취소·마감 신호를 전달한다.
        value, err := s.repo.ListRecent(ctx)
        select {
        case sessionsCh <- result[[]FocusSession]{value: value, err: err}:
            // 호출자가 아직 결과를 받고 있으면 메시지를 전달한다.
        case <-ctx.Done():
            // 요청이 끝났다면 더 이상 결과를 보내려고 막히지 않는다.
        }
    }()

    go func() {
        // 외부 호출도 context를 받는 클라이언트 API로 구성해야 취소를 반영할 수 있다.
        value, err := s.summaryClient.Today(ctx)
        select {
        case summaryCh <- result[Summary]{value: value, err: err}:
        case <-ctx.Done():
        }
    }()

    var dashboard Dashboard
    for remaining := 2; remaining > 0; remaining-- {
        select {
        case sessions := <-sessionsCh:
            if sessions.err != nil {
                return Dashboard{}, sessions.err
            }
            dashboard.Sessions = sessions.value
        case summary := <-summaryCh:
            if summary.err != nil {
                return Dashboard{}, summary.err
            }
            dashboard.Summary = summary.value
        case <-ctx.Done():
            // 클라이언트 연결 종료나 timeout을 상위 handler가 오류 분류하도록 반환한다.
            return Dashboard{}, ctx.Err()
        }
    }
    return dashboard, nil
}
~~~

이 예시는 결과가 두 개라는 사실을 알고 있으므로 각 channel에 크기 1 버퍼를 둔다. 작업 하나가 먼저 실패해 return해도 다른 작업은 ctx.Done 경로를 확인해 송신 대기에 빠질 가능성을 줄인다. 실제 서비스에서는 오류가 나면 즉시 cancel을 호출할지, 부분 결과를 허용할지, 외부 API timeout을 얼마나 둘지를 API 계약으로 결정해야 한다.

## 3. 개념 선택

> 단일 선택: Go HTTP 요청의 context에 관한 설명 중 **옳은 것 하나**를 고르세요.

- [ ] A. context를 전달하면 실행 중인 goroutine이 코드와 무관하게 즉시 강제 종료된다.
- [ ] B. context는 요청 취소·마감 신호를 하위 호출에 전달할 수 있지만, 하위 코드와 사용하는 API가 그 신호를 처리해야 한다.
- [ ] C. context에는 DB 연결, 전역 설정, 모든 업무 입력을 넣는 것이 권장된다.
- [ ] D. 클라이언트가 연결을 끊어도 HTTP 요청 context는 취소될 수 없다.

> [!answer]- 정답과 해설
> - 정답: B
> - 해설: context는 취소 신호를 전달하는 통로다. 실제 중단은 ctx.Done을 확인하거나 context-aware API를 호출할 때 이뤄진다. 의존성은 명시적인 필드·매개변수로 두는 편이 책임을 읽기 쉽다.

## 4. 코드·명령 결과 선택

> 단일 선택: 예시 코드에서 호출자가 응답을 기다리지 않게 된 뒤 sessionsCh 수신자가 사라진 상황에 관한 설명 중 **옳은 것 하나**를 고르세요.

- [ ] A. goroutine은 어떤 경우에도 채널 송신에서 기다리지 않는다.
- [ ] B. 버퍼와 ctx.Done을 함께 두면 작업 결과를 보내지 못해 무기한 막힐 위험을 줄일 수 있다.
- [ ] C. channel은 context를 자동으로 취소하므로 select가 필요 없다.
- [ ] D. result 값의 err 필드는 오류를 전달할 수 없다.

> [!answer]- 정답과 해설
> - 정답: B
> - 해설: buffer 하나만으로 모든 상황을 해결하지는 않지만, 결과 개수와 수신 경로가 명확할 때 대기 경계를 줄인다. ctx.Done을 함께 select하면 요청이 끝난 뒤의 송신을 포기할 수 있다.

## 5. 오류 원인 또는 올바른 코드·설정 선택

> 복수 선택: 동시성 작업의 **오류 원인 또는 올바른 방향을 모두** 고르세요.

- [ ] A. 여러 goroutine이 같은 map을 동시에 수정해도 Go는 자동으로 순서를 보장한다.
- [ ] B. DB·외부 API 호출이 context를 지원하는지 확인하고, 가능하면 요청 context를 전달한다.
- [ ] C. channel을 쓴다는 사실만으로 goroutine 누수와 data race가 자동으로 사라진다.
- [ ] D. 오류가 난 뒤에도 다른 작업을 계속 기다릴지, 취소할지, 부분 응답을 줄지는 API 계약으로 정해야 한다.

> [!answer]- 정답과 해설
> - 정답: B, D
> - 해설: 공유 map 변경은 동기화가 필요하고, channel은 설계를 대신하지 않는다. 실패 후의 정책은 사용자 경험과 데이터 일관성에 영향을 주므로 handler·service 경계에서 명시한다.

## 6. 요청 흐름·환경 차이 선택

> 복수 선택: 요청·데이터 흐름 또는 Linux·Windows·컨테이너 차이를 **올바르게 설명한 것을 모두** 고르세요.

- [ ] A. reverse proxy, systemd, Windows 서비스는 요청 timeout과 프로세스 종료를 항상 같은 방식으로 전달한다.
- [ ] B. React가 요청을 취소할 수 있어도 Go service·repository가 취소를 처리하지 않으면 내부 I/O가 계속될 수 있다.
- [ ] C. 컨테이너에서 SIGTERM을 받는 프로세스의 종료 흐름은 HTTP 요청 context와 별개로 graceful shutdown 설계가 필요할 수 있다.
- [ ] D. 로컬에서 한 번 성공했으면 운영 환경의 외부 API 지연과 연결 풀 제한도 검증된 것이다.

> [!answer]- 정답과 해설
> - 정답: B, C
> - 해설: 브라우저·서버·DB·외부 API의 취소는 하나의 신호가 자동으로 끝내는 일이 아니다. 프로세스 종료와 진행 중 요청의 정리 또한 운영 환경의 정책과 코드의 graceful shutdown을 함께 봐야 한다.
